# Development update — M0 3D laboratory

**Date:** October 27, 2026

**Project lead:** Hiran Tiago Lins Borba · Toronto, ON, Canada

**Milestone:** first executable 3D infrastructure prototype; M0 remains in progress.

**Development assistance:** OpenAI Codex.

## What I implemented

I started the 3D development track by establishing a reproducible Godot 4.7.2
laboratory and a small native C extension. My immediate goal is to validate the
engine/native-library boundary before connecting the existing ALttP gameplay
implementation or producing a complete set of models.

I also built an original geometric scene to test the camera, lighting, shadows
and renderer on my Mac. It is a technical scene, not an extracted ALttP map or
a finished recreation of Link’s house.

![Actual M0 viewport running on macOS with Godot Compatibility](../3d/images/m0-laboratory.png)

*Actual viewport capture from the running prototype. The character-shaped marker

## Technical changes

| Area | Implementation |
| --- | --- |
| Engine | Godot 4.7.2 pinned to official release downloads with SHA-256 checks |
| Native library | C GDExtension probe, ABI revision 1, exact engine-version check |
| Lifecycle | Native initialization and shutdown markers, checked in the actual engine |
| Scene | Procedural meshes, materials, orthographic camera, directional light and shadows |
| Interaction | Camera zoom and exit controls; no gameplay movement |
| Build tools | Python scripts for engine setup, native compilation and headless testing |
| CI | Dedicated macOS Intel/Windows x86_64 probe workflow; no ROM required |
| Release isolation | Existing stable game releases are preserved; M0 produces diagnostic artifacts |

The generated Godot interface header retains its original license notice. The
small extension uses the C interface directly; the future gameplay-facing bridge
and any C++ scene bindings remain separate implementation work.

## What I verified

On macOS, I compiled and loaded the library, checked its ABI, ran the Godot
lifecycle test, and rendered the scene with OpenGL Compatibility on the AMD
FirePro D700. The test verifies that native initialization, scene setup and
native shutdown all occur without engine/script errors.

I also cross-compiled the Windows x86_64 DLL and checked its exported entry
points. This does not establish that it loads in Godot on Windows; that check
still needs the Windows CI runner or the development PC.

The short static frame-time sample is diagnostic only. It is not a gameplay
benchmark or evidence of final performance on either machine.

## What this update does not include

The existing C gameplay core is not connected to the scene. There is no
controllable Link, converted ALttP map, gameplay collision, enemy AI, combat,
original audio or save integration in the new host. The geometry is a blockout,
not the final art style or a set of Nintendo Switch models.

The stable 2D game and the experimental 3D laboratory remain separate. This
milestone does not update the downloadable stable game into a 3D remake.

## My next steps

1. Push the implementation and review the new Windows/macOS CI results.
2. Run the same scene on my i9-14900K / RTX 5060 Ti 16 GB Windows PC with Forward+.
3. Record the actual renderer/driver, a viewport capture and a compatibility comparison.
4. Pin the Blender/export workflow and validate an animated GLB round trip.
5. Finish M0, then start extracting a controlled gameplay-host boundary in C.
6. Introduce copied player/scene snapshots before connecting movement to the view.

The longer-term goal is still a handcrafted diorama presentation inspired by
Link’s Awakening on Nintendo Switch. My first milestone is a small, verified
playable slice, rather than an immediate remake of the whole game.
