# Development update — first C gameplay integration in Godot

**Date:** October 27, 2026

**Project lead:** Hiran Tiago Lins Borba · Toronto, ON, Canada

**Status:** initial M1 integration verified locally on macOS; broader integration remains in progress.

I have connected my Godot laboratory to the existing snesrev/zelda3 C gameplay
implementation. My work in this step is the host separation, native integration,
state interface, input translation, verification tooling and diagnostic view.
The original game logic and reverse-engineering foundation remain credited to
the upstream contributors.

## What I implemented

- A C gameplay host that does not create an SDL window or audio device.
- A native Godot class with commands to open resources, step the game, copy
  snapshots, retrieve a reference image and close the session.
- Fixed-tick input from Godot, with positions and scene state supplied by C.
- Preservation of PPU/HDMA work and muted audio synthesis needed for gameplay feedback.
- Optional read-only SRAM import, with disk writes disabled in this preview.
- A live reference panel from the same simulation and a coordinate-driven marker.
- Local host-comparison, real-engine boundary and AddressSanitizer checks.

## What I verified

I compared every tick of two 1,875-tick routes against a controlled reference
using the original SDL host's loader and helpers. Both routes matched: one
started without an imported save, and one used an existing SRAM file that stayed
unchanged. The comparison included RAM, SRAM, VRAM, SPC RAM, pixels and PCM.

I also verified that Godot and the standalone C library return the same snapshot
after 240 controlled ticks. A 2,000-tick AddressSanitizer route completed without
a reported address error. The Windows DLL cross-compiles, but I have not yet
verified its execution inside Godot on Windows.

These results are scoped regression checks, not a claim of complete game,
original-console, cross-platform or hardware compatibility.

## What still needs work

Audio is synthesized but not played. Saves are not persisted. The diagnostic
reference image uses an interim 10 Hz transfer path. The 3D blockout is not
aligned to the actual area's collision geometry, and there are no finished
character models, game animations or converted maps.

My next steps are native Windows validation, broader gameplay fixtures, proper
PCM/save transport, and a graybox whose objects and doorways align with the
source gameplay. The Blender/animated-GLB pipeline still needs its M0 validation.

This update is a development milestone, not a standalone downloadable 3D game
release. My stable 2D packages remain separate.
